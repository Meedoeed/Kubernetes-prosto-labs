# Лаба 01 - локальный кластер и первый Pod

[К оглавлению](../../README.md) · [Теория](https://habr.com/ru/articles/1082088/) · [Задания](tasks.md) · [Решения](solutions.md)

Поднимем однонодовый кластер kind, найдём компоненты Control Plane и запустим nginx в Pod. На выполнение после установки инструментов ориентировочно потребуется 20–30 минут.

## Подготовка

Установите [Docker Desktop](https://docs.docker.com/desktop/setup/install/) для Windows/macOS или [Docker Engine](https://docs.docker.com/engine/install/) для Linux, затем [kind](https://kind.sigs.k8s.io/docs/user/quick-start/#installation) и [kubectl](https://kubernetes.io/docs/tasks/tools/).

На Windows нужен режим Linux containers. При работе через WSL2 включите интеграцию Docker Desktop с дистрибутивом и выполняйте команды в его терминале. Встроенный Kubernetes Docker Desktop включать не требуется.

Проверьте инструменты:

```bash
docker version
kind version
kubectl version --client
```

**Результат:** команды показывают версии без ошибок. У Docker присутствуют разделы `Client` и `Server`.

**Проверка:** если Docker не показывает `Server`, сначала запустите Docker и устраните ошибку подключения.

## 1. Создание кластера

```bash
kind create cluster --name k8s-first-lab --wait 180s
```

**Результат:** kind успешно завершает создание одной ноды. Первая загрузка образа может занять несколько минут.

На этой ноде будут работать и управляющие компоненты, и приложение. В однонодовом kind это штатная учебная конфигурация.

Выберите подключение и проверьте API:

```bash
kubectl config use-context kind-k8s-first-lab
kubectl cluster-info
```

**Проверка:** в выводе есть `Kubernetes control plane is running at ...`, ошибок подключения нет. kubectl обращается к API Server по указанному адресу.

Если кластер уже существует после предыдущего прохождения, повторное создание не требуется. Выберите его подключение и продолжайте.

## 2. Проверка ноды

```bash
kubectl get nodes
```

**Результат:** в списке одна нода `k8s-first-lab-control-plane` со статусом `Ready`.

**Проверка:** если видите `NotReady`, подождите и повторите команду. Если состояние не меняется, переходите к [диагностике](../../docs/troubleshooting.md).

Колонка `ROLES` содержит `control-plane`. В этом стенде на той же ноде разрешено выполнение обычных приложений.

## 3. Системные компоненты

Namespaces разделяют объекты внутри кластера. Управляющие компоненты нашего стенда находятся в `kube-system`, а приложение создадим в `default`.

```bash
kubectl get pods -n kube-system
```

**Результат:** среди системных подов есть имена с префиксами:

| Префикс | Назначение |
| --- | --- |
| `kube-apiserver-` | Kubernetes API |
| `etcd-` | Хранение состояния API |
| `kube-scheduler-` | Назначение нод новым подам |
| `kube-controller-manager-` | Работа встроенных контроллеров |

**Проверка:** найдите все четыре компонента и вспомните роль каждого. В списке будут и другие системные поды.

kubelet работает как служба в операционной системе ноды, вне Pod. Поэтому `kubectl get pods` его не показывает.

## 4. Запуск приложения

```bash
kubectl run hello-k8s --image=nginx:stable-alpine
kubectl get pods
```

Первая команда создаёт Pod `hello-k8s` с контейнером nginx. При стандартном подключении к только что созданному кластеру он окажется в `default`.

**Результат:** после подготовки контейнера статус становится `Running`, а готовность - `1/1`.

Пример ожидаемого вывода:

```text
NAME        READY   STATUS    RESTARTS   AGE
hello-k8s   1/1     Running   0          30s
```

**Проверка:** если сначала видите `Pending` или `ContainerCreating`, повторите `kubectl get pods` через несколько секунд. При ошибке загрузки образа прочитайте раздел диагностики.

Если Pod уже существует, не повторяйте `run`: проверьте состояние существующего объекта.

## 5. Нода и события запуска

```bash
kubectl get pods -o wide
kubectl describe pod hello-k8s
```

**Результат:** колонка `NODE` и поле `Node` указывают на `k8s-first-lab-control-plane`. В разделе `Events` обычно видны события `Scheduled`, `Pulled`, `Created`, `Started`.

**Проверка:** сопоставьте результат с последовательностью:

1. kubectl отправил запрос в API Server.
2. Объект Pod был сохранён через API, состояние хранится в etcd.
3. Scheduler назначил ноду.
4. kubelet на ней обеспечил запуск контейнера через контейнерный движок.

События хранятся ограниченное время. Их отсутствие при повторном просмотре старого Pod само по себе не означает ошибку.

## Завершение

Кластер можно оставить для дальнейшей практики. Он продолжит использовать ресурсы компьютера.

Если стенд больше не нужен:

```bash
kind delete cluster --name k8s-first-lab
```

Команда удалит учебный кластер вместе с приложением. Не выполняйте её до завершения самостоятельных заданий.
