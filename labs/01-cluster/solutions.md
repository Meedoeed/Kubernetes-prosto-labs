# Решения - лаба 01

[К заданиям](tasks.md) · [К памятке](README.md)

Сначала попробуйте выполнить задания самостоятельно. Примеры ниже предполагают выбранное подключение `kind-k8s-first-lab` и стандартный namespace `default`.

## 1. Нода

```bash
kubectl get nodes
```

Ожидается нода `k8s-first-lab-control-plane` в состоянии `Ready`. Версию берём из колонки `VERSION`; конкретное значение зависит от установленного стенда.

## 2. Компоненты Control Plane

```bash
kubectl get pods -n kube-system
```

В стандартном стенде имена будут такими:

| Имя | Роль |
| --- | --- |
| `kube-apiserver-k8s-first-lab-control-plane` | Обрабатывает запросы Kubernetes API |
| `etcd-k8s-first-lab-control-plane` | Хранит состояние API |
| `kube-scheduler-k8s-first-lab-control-plane` | Назначает ноду Pod, у которого её ещё нет |
| `kube-controller-manager-k8s-first-lab-control-plane` | Запускает встроенные контроллеры |

Для сравнения используйте фактические имена из своего вывода.

## 3. Расположение приложения

```bash
kubectl get pods -o wide
kubectl describe pod hello-k8s
```

В первом выводе смотрим `NODE`, во втором - `Node`. Оба указывают на `k8s-first-lab-control-plane`; в подробном описании после имени может присутствовать адрес ноды.

## 4. События запуска

```bash
kubectl describe pod hello-k8s
```

В разделе `Events` ищем:

| Событие | Что произошло |
| --- | --- |
| `Scheduled` | Pod назначен ноде |
| `Pulling` | Началась загрузка образа, если она потребовалась |
| `Pulled` | Образ загружен или уже присутствует на ноде |
| `Created` | Контейнер создан |
| `Started` | Контейнер запущен |

Список не обязательно совпадёт полностью: образ может быть уже загружен, а старые события со временем удаляются. Отсутствие старых событий не доказывает, что запуск не происходил.

## 5. Пространства имён

```bash
kubectl get pods -n kube-system
kubectl get pods -n default
```

`-n` выбирает namespace. В `kube-system` находятся системные поды, в `default` - созданное нами приложение. Команды показывают разные выборки объектов одного работающего кластера.

В исходной лабе `kubectl get pods` без `-n` обращается к `default`. Вообще namespace по умолчанию можно изменить в настройках подключения, поэтому явное указание удобно для сравнения.

## 6. Второй Pod

```bash
kubectl run hello-again --image=nginx:stable-alpine
kubectl get pods -o wide
kubectl get nodes
```

Если контейнер ещё готовится, повторите вторую команду через несколько секунд. Ожидаются `hello-k8s` и `hello-again` со статусом `Running`, готовностью `1/1` и одной нодой `k8s-first-lab-control-plane`.

Создание нового Pod не создаёт новую ноду. Несколько подов могут работать на одной ноде.

Если `hello-again` уже существует после прошлой попытки, `run` вернёт `AlreadyExists`. Проверьте существующий Pod, повторное создание не требуется.

## Ответы на вопросы

1. kubectl обращается к API Server.
2. Scheduler выбирает ноду для ещё не назначенного Pod.
3. kubelet на выбранной ноде обеспечивает запуск через контейнерный движок.
4. В нашем стенде kubelet работает как служба в ОС ноды, вне Pod. Список подов не является списком всех процессов ноды.
5. Однонодовый kind настроен так, чтобы управляющие компоненты и обычные приложения могли работать на единственной ноде. Разделение их задач при этом сохраняется.
